🐛 Bug
To Reproduce
This is a slightly complex use case: running pytorch distributed on 2 nodes with 8 GPUs each, but we use only a single rank/GPU per node (for testing purposes).
Steps to reproduce the behavior:

Need a cluster with 2 separate nodes, and each node must have 2 or more GPUs.
Create a simple pytorch code that does torch.distributed.barrier() followed by torch.distributed.all_reduce(x)



Run the official 1.8.0 pytorch container on those 2 nodes (in our case we use the Slurm resource manager + the pytorch distributed launcher)



As you can see above, the code hangs and never prints the tensor.

I'm providing debug details in the "Additional context" section below,  the root cause seems to be that calling torch.distributed.barrier() immediately after init_process_group causes global rank 1 to unfortunately choose GPU 1 to perform this barrier:



pytorch/torch/lib/c10d/ProcessGroupNCCL.cpp


        Lines 1383 to 1390
      in
      9f2aea7






 // This means there is not yet a NCCL collective being called 



 // Here we have to use the best guesses and will use a single GPU to call 



 // allreduce to achieve barrier. 



 // In case the multiple processes fall into the same node, we use rank to 



 // ensure that each process is on a different GPU 



 auto numGPUs = at::cuda::getNumGPUs(); 



 int16_t deviceIdx = static_cast<int16_t>(rank_ % numGPUs); 



 devices.emplace_back(at::DeviceType::CUDA, deviceIdx); 





Then, when calling all_reduce, rank 1 will try to create a new NCCL communicator, whereas rank 0 will not, so it's a deadlock.
Perhaps the local rank should be used instead of the global rank in the code above? Or perhaps the device_ids argument of the barrier function should default to the current device? Today torch.cuda.set_device has no impact on this behavior.
There are 2 known workarounds today:

Set CUDA_VISIBLE_DEVICES=0, to hide other GPUs that shouldn't be used.
Force the barrier to be on the GPU we want: torch.distributed.barrier(device_ids=[local_rank])

Expected behavior
The pytorch code is expected to print the tensor and terminate. Using only 1/8 GPU per node might be unusual, but this hang was tricky to debug, and it was especially confusing since all_reduce then barrier works fine, but barrier then all_reduce doesn't:

PyTorch Version (e.g., 1.0): 1.8.0

Additional context
Rank 0 has a context active on GPU 0 only, as expected, and is blocked on cuMemcpyDtoHAsync_v2:

It is likely waiting for the NCCL collective to finish, but it never happens since rank 1 is not participating in this collective.
Rank 1 has a context active on both GPU 0 and GPU 1, because the global rank was used when the barrier was called.

And it is blocked on broadcastUniqueNCCLID:

I believe this rank is trying to create a new NCCL communicator because it has no cached communicator for GPU 0 (as the barrier was done on GPU 1).

Mixed Precision frequently runs into unsupported operator for the lower precision issue, or just worse / degraded accuracy if some operators / modules are run in lower precision.
For FSDP native mixed precision, if users are aware of these operators and the modules that they belong to, it could be useful to simply exclude these modules from mixed precision and still get the performance enhancements by having rest of the module in mixed precision.
One useful API might be to ignore some modules for mixed precision, or the reverse direction, specify explicitly which modules to be mixed precision.
