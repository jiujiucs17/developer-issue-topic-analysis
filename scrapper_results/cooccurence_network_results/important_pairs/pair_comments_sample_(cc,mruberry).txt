----------------------------------------Comment 2----------------------------------------

Overview
Implementing a correct meta device initialization is challenging with either leaking FSDP into the nn.Module definition or leaking FSDP's private functions/attributes (_is_fsdp_flattened()). See this issue for the full context.
One "supported" method for meta device initialization is to have the model's modules implement reset_parameters() or for the user to pass in a param_init_fn: Callable[[nn.Module], None]. However, the current implementation is problematic for two reasons:

nn.Module.to_empty() is recursive. It will reset already-initialized parameters in the case of nested FSDP wrapping.
Only calling reset_parameters() with the FSDP-wrapped module (and not submodules) means that FSDP expects reset_parameters() to reset submodules' parameters, which violates the method's expected contract and requires unnecessary code duplication (to recurse into submodules) in possibly every reset_parameters() implementation.

Proposed Solution
The proposed solution is to change FSDP's contract: nn.Module.reset_parameters() or the user's custom param_init_fn: Callable[[nn.Module], None] should only initialize the given module's parameters and not those of its submodules. This means that for the param_init_fn, I likely expect it to condition on the nn.Module type.
FSDP will make sure to only call reset_parameters() or the custom param_init_fn once per module throughout construction time and only on modules with parameters (i.e. len(list(module.parameters(recurse=False))) > 0).

🐛 Bug

The above returns an image full of 1's. However, some would expect it to return an image full of zeros -- each grid coordinate is (-5, -5), which is definitely beyond the [-1, 1] boundaries for the image, so the value should be the padding value.
I'm not completely convinced that this is a bug. When align_corners=True and the image only has a single pixel, each of the corners (-1, -1), (1, -1), (-1, 1), (1, 1) are mapped to the center of the pixel. Since they're all the same location, the geometry becomes weird -- if the distance between (-1, -1) and (1, 1) is 0, then what's the distance between (-5, -5) and (-1, -1)?
Perhaps the way to resolve this is to add a warning in the documentation and/or add a warning to the code if any inputs have height or width 1.
