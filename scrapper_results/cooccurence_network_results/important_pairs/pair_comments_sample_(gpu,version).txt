🐛 Bug
Under ceil_mode=True for AvgPooling2d, Pytorch fails in calculating pooling output shape as expected, and gets NaN results, no matter executing with CPU version or GPU version.
Taking Pytorch with CPU version as an example, given an input with the shape (1, 16, 4, 4), I get an unexpected output under layer the AvgPool2d , which contains NaN(Not a Number) results，as shown in the following picture.

In this case, the parameters of AvgPool2d are as follows:

To investigate the root cause of such NaN results, I conduct a code tracing in the source code of Pytorch when executing AvgPool2d. Relevant code can be found inaten/src/ATen/native/Pool.h  and aten/src/ATen/native/AveragePool2d.cpp.
Firstly, Pytorch invokes the function pooling_output_shape_pad_lr in aten/src/ATen/native/AveragePool2d.cpp line 129-130  to calculate to pooling output shape.

Then Pytorch passes the two parameters outputHeight and outputWidth to function avg_pool2d_out_frame in aten/src/ATen/native/AveragePool2d.cpp (near line 14) to calculate the average pooling for each pool unit.
The implementation of pooling_output_shape_pad_lr is defined in aten/src/ATen/native/Pool.h (near line 25) . See the following picture.

The parameter ceil_mode=True indicates Pytorch uses ceil value instead of floor value when getting an output (refer to the official  website). For pooling calculations,  the ceil_mode=True may make the last pool unit start outside the image. From the above code, we know that Pytorch tries to avoid such condition  by executing --outputsize. This indeed works, but is only be triggered when using padding on this dimension (seeif(pad_l) line 31). In other words, if there is no padding  (pad_l=0) on this dimension, the outputsize will not be reduced by 1.
As a result, passing the output shape (also called out-of-range output shape) to avg_pool2d_out_frame, it will cause the last pool unit to be outside the image, as shown in the following example.

To be specific, an out-of-range output shape will generate a hstart(or wstart) whose value is greater or equal to hend（or wend), thus making the pool_size=(hend-hstart)*(wstart-wend) be zero or a negative value,  as shown between the line 46-83 in  aten/src/ATen/native/AveragePool2d.cpp.

In particular, just as our example, when hstart=hend (or wstart=wend ), it will make poolsize = 0,divide_factor=0 andsum = 0. Consequently,  the corresponding average pooling unit is calculated with  0 divided by 0, thus triggering NaN. Actually, the premise of function avg_pool2d_out_frame is that hstart  and wstart  are always smaller than hend and wend, and this needs to be guaranteed by the previous function pooling_output_shape_pad_lr in pool.h. But due to if (pad_l), it only executes the relevant judgments and reductions when using padding on this dimension.
In addition, I also try multiple sets of other different parameters. They all trigger the NaN problem
on both CPU and GPU version, because of the same reason (hstart=hend), as shown in the following table.
